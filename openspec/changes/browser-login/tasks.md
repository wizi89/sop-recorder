## 2. Callback parsing (spec: user-authentication)

- [x] 2.1 Add `pub fn parse_callback(url: &Url) -> Result<(String, String), CallbackError>` to `network/auth.rs`, returning `(code, state)` from the query. ## 3. Code exchange (spec: user-authentication)

- [x] 3.1 Add `pub async fn complete(p: &PendingLogin, code: &str, api_base: &str) -> Result<Tokens, String>` to `network/auth.rs`: POST `{code, code_verifier}` to `/auth/desktop/exchange`, deserialize into the existing `SignInResponse`, and **return the tokens without writing the keyring**. This is the one place it must not copy `sign_in`, which saves before it returns: `complete()` runs inside a cancellable `select!` (5.1d), so persisting there would let a cancel that wins the race leave a stored refresh token behind a UI that said the sign-in was cancelled. The command performs the save, reusing the existing keyring-save path unchanged, once the `select!` has resolved in the exchange's favour; **the command's** keyring writes and `AuthSession` construction are identical to `sign_in`'s (`network/auth.rs:78`). What is not identical to `sign_in` is **the error handling**. `sign_in` never inspects `res.status()` -- it parses the body and falls back to the literal `"Anmeldung fehlgeschlagen"` when no token is present, so a 404 body of `{"detail":"Not Found"}` from an API without the endpoint, or an HTML error page from the proxy, would surface as an ordinary failed login. `complete` therefore branches on the status first and returns a distinct "server does not support browser sign-in" error for 404 and 405, and for a body it cannot parse as JSON. Its `reqwest` client is built with a **15-second timeout** -- `sign_in`'s `reqwest::Client::new()` has none, so copying it wholesale would make a hung backend unbounded. Verify with unit tests over each of those three responses, a server that accepts the connection and never answers (asserting the call returns a timeout error rather than hanging), and the happy path.
- [x] 3.1b Surface that error distinctly in the UI: it is the one login failure that should send the user to the fallback rather than ask them to try again. Verified by the test added in 6.5 and end to end by 7.7.
- [x] 3.1c Define `Tokens { access_token, refresh_token, email }` next to `complete()` -- the three fields the command needs for the keyring save and the `AuthSession`. It exists only so that the exchange's result can cross the `select!` boundary without having been persisted on the way (3.1); `SignInResponse` stays the deserialization target.
- [x] 3.2 Confirm `SignInResponse` needs no new fields: the exchange response shape is fixed by the contract to match `/auth/signin`. If the server-side change deviates, fix the server, not this struct.

## 4. Loopback listener (spec: user-authentication)

- [x] 4.1 Add `src-tauri/src/network/loopback.rs` with `Callback { redirect_uri, .. }`, `start_loopback()` binding `127.0.0.1:0`, and `Callback::recv(timeout, &cancel)`, which selects over the accept loop, the timeout and the attempt's cancel token so that cancelling while waiting for the browser drops the listener at once. It **accepts connections in a loop** until a well-formed `/callback` arrives or the attempt ends, reading each request line under a 5-second deadline, parsing the target with `url::Url`, resolving with the `Url` plus a `Reply` that keeps the callback connection open, and dropping anything else. A one-shot `accept()` is wrong here and task 4.5 is the test that catches it. Verify with a Rust test that connects to the bound port with a raw `TcpStream`, sends `GET /callback?code=X&state=Y HTTP/1.1`, and asserts `recv` yields a `Url` carrying both values and that the stream has received no response yet.
- [x] 4.1b Add `Outcome` (success, or a failure reason from the fixed set `verification`, `denied`, `expired`, `unsupported`, `error`) and `Reply::finish(&Outcome)`, which writes a `302` to `{webapp}/desktop/signed-in` or `{webapp}/desktop/sign-in-failed?reason=<token>` and closes the connection. Dropping a `Reply` without `finish` writes the `reason=error` redirect. Verify with Rust tests reading the raw response from the `TcpStream`: success gives a `302` with the signed-in `Location`; each failure gives its reason token; a dropped `Reply` gives `reason=error`; no response contains the code, the state or an email.
- [x] 4.1c Bound `finish` at 20 seconds after the callback: if the outcome is not known by then, send the `reason=error` redirect and let the command finish on its own. The rule is the strict ordering in design.md -- server upstream bound (10) < recorder exchange deadline (15) < `finish` bound (20) -- because `finish` runs only after the exchange returns. Equal values are a bug: an exchange that succeeds in the last milliseconds loses to a timer that started at the same moment, and the tab reports failure while the app signs in. Verify with a test that holds the `Reply` past a shortened bound and asserts the stream received the error redirect.
- [x] 4.2 Verify the listener binds loopback only, with a test asserting the bound address is `127.0.0.1` and the port is non-zero.
- [x] 4.3 Verify a malformed request is answered with 400 and does not resolve `recv`, with a test sending `GARBAGE\r\n\r\n` and asserting the receiver is still pending.
- [x] 4.4 Verify `recv` returns a timeout error and releases the port, with a test using a 50 ms timeout and then rebinding the same port.
- [x] 4.5 Verify a silent connection cannot strand the attempt: open a TCP connection to the bound port, send nothing, then open a second connection carrying a valid callback, and assert `recv` resolves from the second without waiting out the first. This is the browser-preconnect case, and a one-shot `accept()` fails it.
- [x] 4.6 Add the module to `network/mod.rs` with a file-level comment naming it as the deep-link swap point, so the next change knows exactly what to delete.
